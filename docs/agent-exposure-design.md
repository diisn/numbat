# 本地 Agent 对外暴露服务的设计总结

## 1. 目标

让运行在本地机器上的 Agent 能够安全、可扩展地对外提供服务，同时支持：

- **WebUI**：用户在浏览器里与 Agent 交互。
- **第三方 IM 平台**：例如飞书、Telegram、WhatsApp 等。

对外暴露的不是 Agent 本身，而是一个**网关层**。网关负责接收外部请求、维护长连接、把消息路由给 Agent、再把 Agent 的响应返回去。

---

## 2. 整体架构

```
外部客户端（浏览器 / 飞书 / Telegram）
            │
            
      HTTP / WebSocket 网关
            │
            ├── 静态资源服务（WebUI）
            ├── WebSocket 连接管理
            ├── 健康检查 / 指标 / 日志
            └── 通道接入管理
            │
            ▼
      通道适配层（Channel）
            │
            ▼
      消息路由层（Router）
            │
            ▼
      Agent 执行层
            │
            ▼
      会话 / 记忆 / 工具 / LLM
```

---

## 3. 需要实现的模块

### 3.1 HTTP 网关模块

**职责**

- 提供统一的对外入口。
- 处理普通 HTTP 请求：健康检查、指标、日志、配置页面等。
- 挂载静态资源（WebUI）。
- 把 `/ws` 路径交给 WebSocket 模块处理。
- 可选：认证、CORS、请求恢复、限流等通用中间件。

**应该怎么做**

- 使用一个高性能的 HTTP Router（如 gin）。
- 注册基础路由：
  - `GET /health`：健康检查。
  - `GET /metrics`：Prometheus 指标。
  - `GET /logs` / `/logs/stream`：日志查看与流式日志。
  - `GET /settings`：配置页面与配置接口。
  - `GET /app/*`：WebUI 静态资源。
  - `GET /ws`：WebSocket 升级入口。
- 配置 `http.Server` 时注意 WebSocket 长连接不要设置写超时。
- 静态资源可以用前端构建产物嵌入二进制，运行时通过文件系统或 embed 提供。

---

### 3.2 WebSocket 通信模块

**职责**

- 把 HTTP 连接升级为 WebSocket 长连接。
- 维护与前端客户端的双工通信。
- 定义前后端交互协议。
- 分发请求到不同的业务处理器。
- 管理连接生命周期：限流、重连、断开清理。

**应该怎么做**

- 使用成熟的 WebSocket 库处理协议升级。
- 定义统一的协议：推荐 JSON-RPC 2.0，每个请求包含 `method`、`params`、`id`。
- 在服务端实现一个 `dispatch` 方法，按 `method` 路由到不同处理函数，例如：
  - `chat.send`：发送消息给 Agent。
  - `chat.abort`：取消当前 Agent 运行。
  - `chat.approve`：用户对工具调用进行审批。
  - `session.list` / `session.new` / `session.switch`：会话管理。
  - `jobs.list` / `jobs.pause` / `jobs.resume`：任务管理。
- 每个连接内维护：
  - 当前运行的 Agent 取消函数，用于中断。
  - 用户审批的等待通道。
  - 会话状态。
- 实现限流：例如令牌桶，限制单连接每秒消息数，防止滥用。
- 实现来源检查：配置允许的 Origin，防止跨站 WebSocket 攻击。
- 断开时清理资源：取消正在运行的 Agent、关闭通道、释放会话引用。

---

### 3.3 通道接入模块（Channel）

**职责**

- 把不同的外部 IM 平台抽象成统一的接口。
- 每个平台写一个适配器，实现同样的收发逻辑。
- 让系统可以无差别地处理飞书、Telegram、WhatsApp 等。

**应该怎么做**

- 定义统一的 `Channel` 接口：
  - `Connect()`：建立连接。
  - `Disconnect()`：断开连接。
  - `Send()`：发送消息给用户。
  - `Receive()`：接收用户消息。
  - `Status()`：返回通道状态。
- 每个平台实现一个 Channel：
  - **飞书**：使用官方 SDK 的 WebSocket 长连接模式，监听消息事件，不需要公网 Webhook。
  - **Telegram / WhatsApp**：使用各自的 Bot API 或第三方库轮询 / WebSocket。
- 通道适配器内部需要处理：
  - 平台事件去重（防止重推）。
  - 媒体文件下载。
  - 消息格式转换（把平台消息转成内部统一消息）。
  - 回复格式转换（把 Agent 输出转成平台可读格式，例如 Markdown 转纯文本）。

---

### 3.4 通道管理模块

**职责**

- 启动和停止所有已注册的 Channel。
- 监听每个 Channel 的入站消息。
- 把入站消息交给路由层。
- 把 Agent 的回复通过正确的 Channel 发回。
- 保证同一个发送者的消息串行处理，避免会话冲突。

**应该怎么做**

- 在启动时读取配置，创建对应的 Channel 实例并注册。
- 为每个 Channel 启动独立的 goroutine 监听 `Receive()`。
- 为每个发送者维护一个队列或单 goroutine 处理，保证顺序。
- 收到入站消息后：
  - 提取发送者 ID、通道名、消息内容。
  - 交给 Router 决定用哪个 Agent 处理。
  - 构建 Agent Runtime 并运行。
  - 收集 Agent 输出，调用对应 Channel 的 `Send()` 回发。

---

### 3.5 消息路由模块

**职责**

- 决定一条入站消息应该由哪个 Agent 处理。

**应该怎么做**

- 配置规则，按优先级匹配：
  - 发送者 ID 精确匹配。
  - 发送者类型匹配。
  - 账号 ID 匹配。
  - 通道名匹配。
  - 默认 Agent。
- 返回目标 Agent 的配置（模型、系统提示、可用工具等）。
- 如果匹配失败，使用配置的默认 Agent 或拒绝处理。

---

### 3.6 Agent 执行模块

**职责**

- 运行 Agent 的核心逻辑：LLM 调用、工具调用循环、事件生成。

**应该怎么做**

- 为每次请求创建一个 `Runtime`，包含：
  - 当前会话上下文。
  - 可用的 LLM Provider。
  - 工具注册表。
  - 配置参数（温度、最大步数等）。
- 运行 Agent 主循环：
  - 调用 LLM。
  - 解析工具调用请求。
  - 执行工具。
  - 把结果喂给 LLM。
  - 循环直到完成或出错。
- 通过事件流输出结果：
  - `text_delta`：文本增量。
  - `tool_call_start` / `tool_result`：工具调用。
  - `approval_required`：需要人工审批。
  - `done` / `error` / `aborted`：结束状态。
- 支持取消：通过 `context.Cancel` 或自定义信号中断执行。
- 支持审批：工具调用前暂停，等待用户决策。

---

### 3.7 会话与记忆模块

**职责**

- 保存每个会话的历史消息。
- 管理会话创建、切换、清空、压缩。
- 提供上下文给 Agent。

**应该怎么做**

- 会话存储在本地文件或轻量级数据库中。
- 每个会话有一个唯一 Key，关联到发送者和 Agent。
- 提供接口：
  - 创建会话。
  - 列出会话。
  - 切换会话。
  - 获取历史。
  - 清空历史。
  - 压缩历史（把旧消息总结成摘要，减少 Token）。

---

### 3.8 WebUI 前端模块

**职责**

- 提供用户与 Agent 交互的界面。
- 通过 WebSocket 与后端通信。

**应该怎么做**

- 使用 React / Vue 等框架构建 SPA。
- 封装一个 WebSocket 客户端类：
  - 连接 `/ws`。
  - 自动重连。
  - 发送 JSON-RPC 请求。
  - 订阅后端事件并更新 UI。
- 页面包括：
  - 聊天页：发送消息、展示流式回复、展示工具调用、处理审批。
  - 会话页：管理会话。
  - 任务页：查看定时任务。
  - 设置页：配置 Agent、LLM、通道等。
- 构建产物通过 HTTP 网关的静态资源路由提供。

## 4. 关键数据流

### 4.1 WebUI 请求流

```
浏览器打开 WebUI
  │
  ▼
HTTP 网关返回 index.html 和静态资源
  │
  ▼
前端 WebSocket 客户端连接 /ws
  │
  ▼
用户发送消息 → 前端发送 chat.send
  │
  ▼
后端 WebSocket dispatch 到 chat 处理器
  │
  ▼
加载会话 → 构建 Runtime → 运行 Agent
  │
  ▼
Agent 产生事件流 → 通过 WebSocket 推给前端
  │
  ▼
前端根据事件类型更新 UI
```

### 4.2 IM 平台消息流

```
用户在企业微信/飞书/Telegram 发送消息
  │
  ▼
平台推送到 Channel 适配器
  │
  
Channel 转成内部 InboundMessage
  │
  ▼
ChannelManager 交给 Router
  │
  ▼
Router 选择目标 Agent
  │
  ▼
运行 Agent，得到输出
  │
  ▼
ChannelManager 调用对应 Channel.Send
  │
  ▼
平台把消息展示给用户
```

## 5. 设计原则

| 原则 | 说明 |
| --- | --- |
| **统一入口** | 所有外部流量都走同一个 HTTP / WebSocket 网关。 |
| **统一协议** | 前后端使用 JSON-RPC 2.0，事件驱动。 |
| **平台无关** | Channel 接口隔离不同 IM 平台的差异，新增平台只需新增适配器。 |
| **会话隔离** | 每个发送者有自己的会话，互不干扰。 |
| **可取消与可审批** | Agent 运行必须能被中断，关键工具调用必须能暂停等待用户确认。 |
| **本地优先** | 数据默认落盘本地，不依赖外部数据库。 |
| **安全** | 认证、来源检查、限流、连接清理缺一不可。 |

---

## 6. 总结

要让一个本地 Agent 对外暴露服务，核心不是把 Agent 直接挂到网上，而是搭建一个**网关层**：

1. **HTTP 网关**提供静态资源和基础接口。
2. **WebSocket 模块**提供与前端的双工实时通信。
3. **Channel 接入层**统一封装各种 IM 平台。
4. **通道管理器**调度消息、串行处理、回发结果。
5. **路由模块**决定谁的消息交给哪个 Agent。
6. **Agent 执行层**运行 LLM 和工具，产生事件流。
7. **会话模块**管理上下文和历史。
8. **前端 WebUI**通过 WebSocket 与后端交互。

这套结构的好处是：新增一个 IM 平台，只需要实现一个 Channel；改进前端交互，只需要改 WebSocket 协议和前端页面；Agent 本身不需要关心消息从哪里来、回复到哪里去。
